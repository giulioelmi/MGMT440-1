## 1. What LUMINA is

LUMINA is a homemade **Perplexity**: an "answer engine". You type a question; it searches the web
(and/or PDFs you uploaded), reads the pages, and writes an answer that streams in word by word,
with numbered citations like `[1]` that point to the exact pages it read.

It has three "gears":

| Gear | What it does | Example |
|---|---|---|
| **Quick search** (default) | One search, reads the top 3 pages, answers in a few seconds | "What is a TTL index in MongoDB?" |
| **Deep search** (opt-in) | First makes a **plan** of 4 smaller questions, researches each one, then writes a long structured answer with ~12 sources | "Compare SSE, WebSockets and long polling for streaming an LLM answer, and what breaks behind a CDN?" |
| **Documents** | Answers from PDFs/Markdown you uploaded, citing the page | "What is the default k1 in BM25?" → "1.2 [1]" with `retrieval-basics.pdf, p. 1` |

It also has **memory**: tell it "remember I prefer short answers" and every later conversation follows that.

This is **MGMT440 Assignment 1**. The course gave us the website (the UI), the rules and the grader.
**We built the two back-office programs** behind the website.

## 2. How it fits together (the restaurant picture)

| Piece | Restaurant role | Folder | Port | Who built it |
|---|---|---|---|---|
| **Website (UI)** | the dining room: what customers see | `web/` | 5173 | the course (**don't edit**) |
| **Gateway** | the waiter: checks who you are, turns away bad orders, carries orders to the kitchen and the food back | `backend/gateway/` | 8787 | Zahid |
| **Agent** | the kitchen: does all the real work (searching, reading, writing answers). Holds all the secret keys | `backend/agent/` | 8000 | first teammate + Zahid |
| **Worker** | the prep cook: processes uploaded PDFs in the background | inside `backend/agent/` | (none) | first teammate |
| **Database** | the pantry: MongoDB Atlas (in the cloud) stores everything | (cloud) | (none) | you set up your own (section 6) |

**The golden rule of the layout:** the website only talks to the gateway; the gateway only talks to
the agent; only the agent holds passwords (API keys). So no key can ever leak to a browser.

A question's journey:
```
You type a question in the browser (5173)
  → gateway (8787): "do you have a user id? is the request valid? not too many requests?"
    → agent (8000): search the web, read pages, ask Claude to write the answer
    ← agent streams the answer back, word by word
  ← gateway passes each word straight through (no waiting)
← the browser shows words as they arrive, with citation chips
```

The AI models used:
- **Claude Sonnet 5** writes every answer (`LLM_MODEL`).
- **Claude Haiku 4.5** writes deep search's plan only, because it's faster (`PLANNER_MODEL`, see 3.3).
- **OpenAI embeddings** turn text into numbers so documents and memories can be searched by meaning.
- **Tavily** is the web search engine.

### 3.3 Zahid: deep search and the rest of Phase 2

All in `backend/agent/src/ask.ts`.

**How a deep search works:**
1. **Spend check.** Each user gets 5 deep searches a day (`DEEP_DAILY_CAP`). The 6th → `429` with
   `resetsAt` (next midnight UTC). The counter is in the `deepUsage` collection.
2. **Plan.** Haiku splits the question into **4 sub-questions**, each with a short reason. The plan is
   sent to the browser **first, before any searching** (the grader checks this), within ~3–4 s.
   The planner is told to split by "what decides the answer" (e.g. cost, failure modes, support),
   never one sub-question per option, no overlaps, one about real-world practice, and never to add
   assumptions the user didn't state.
3. **Research.** Up to 3 sub-questions at a time: each gets its own web search and reads up to 3 pages
   no other sub-question has read. Every step and every source is labelled with its sub-question number.
4. **Answer.** Sonnet writes: a short direct answer, one section per sub-question, then
   "What is still unknown". One shared numbering for all ~12 sources.

**Why Haiku for the plan:** the plan must appear within 4 s (p95). Sonnet took ~4.1 s for the plan
alone (6–13 s before tuning). Splitting a question is easy work; Sonnet still writes the answer.
If the first planner call is stuck, a second identical one is started ("hedging") and the first good
plan wins.

**Other changes:** quick search now searches again when results are off-topic; `/stats` reports
`deepToday` from the spend counter and first-token time for quick answers only.

## 9. When something goes wrong

| You see | Why | Fix |
|---|---|---|
| `"db":"down"`, or `502 ... Topology is closed` | Your free Atlas cluster **paused** (it does this when idle) | Atlas → your cluster → **Resume**, wait 1–3 min, restart the agent (Ctrl+C, `npm run dev:agent`) |
| `bad auth` / `authentication failed` | Wrong database password in `.env` | Fix `MONGODB_URI`; use letters/numbers only |
| `ENOTFOUND` / `querySrv` | Wrong cluster address | Copy the connection string again from Atlas |
| Timeout connecting to the database | Your IP isn't allowed | Atlas → Network Access → Add current IP address |
| Upload stuck at `pending` | Worker not running, or indexes not ready | Check the agent terminal for errors; `node scripts/create-indexes.mjs --status` |
| `401` | No `X-User-Id` header | Expected for requests without it |
| `429` on deep search | Daily deep cap reached (5/day per user) | Use a different `x-user-id`, or wait until midnight UTC |
| `429` on asks | Rate limit (30 asks/uploads a minute per user) | Wait a minute |
| `502` with a message | A provider (Anthropic/Tavily/OpenAI) failed, or the agent is down | Read the message; check keys in `.env`; check the agent terminal. A 502 is the system telling the truth, not hiding it |
| Words arrive all at once | Buffering somewhere | Report it; it's a gateway/agent bug |
| `EADDRINUSE` | A previous run is still using the port | Close old terminals, or `lsof -i :8000` / `:8787` and stop that process |
| `Cannot find module '@lumina/contract'` | The rulebook package wasn't built | `npm run build -w @lumina/contract` (`npm run dev` does this for you) |

Stuck for more than 15 minutes? Message Zahid with the exact command, the exact output, and what you expected.

## 11. Glossary

| Word | Meaning |
|---|---|
| **API key** | A password a program uses to talk to a service (Anthropic, Tavily, …) |
| **Atlas / M0** | MongoDB's cloud database; M0 is the free size |
| **Citation `[n]`** | A number in the answer pointing to source n in the list |
| **Contract** | The rulebook (`packages/contract`): exact shapes of every request and response |
| **Deep search** | The slow, thorough gear: plan → research each part → structured answer |
| **Embedding** | Turning text into a list of numbers so "similar meaning" can be searched |
| **Endpoint / route** | An address on the server, like `POST /threads/:id/ask` |
| **Gateway** | Our front-desk server (port 8787); the only thing the website talks to |
| **Hedging** | Starting a second identical request if the first seems stuck; using whichever finishes first |
| **Indexed** | An uploaded document is fully processed and searchable |
| **p95** | "95% of the time it's at least this fast": the slowest 1 in 20 sets the number |
| **Plan / sub-question** | Deep search's list of smaller questions it researches separately |
| **Rate limit** | A cap on how many requests one user can make per minute |
| **Run log / receipt** | `runs/<requestId>.json`: what one answer did, step by step, with times and cost |
| **Space** | A folder of uploaded documents you can ask questions about |
| **SSE / streaming** | Sending the answer piece by piece as it's written, instead of all at the end |
| **Status codes** | `200` ok · `201` created · `202` accepted, working on it · `204` done, nothing to return · `400` bad request · `401` who are you? · `404` not found · `429` too many · `502` something behind me failed |
| **Thread** | One conversation |
| **TTFT** | Time to first token: how long until the first word appears |
| **Worker** | Background program that processes uploads |
